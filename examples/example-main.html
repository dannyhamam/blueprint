Add rate limiting to the public API

Stop a single API key from starving everyone else, without adding infrastructure or breaking well-behaved clients.

Sep 24, 2026 uppi-order-portal · main Proposal Scope · M 6 steps · ~3 days

01Summary

Three times this month one integration partner's retry loop pushed p99 latency past 4s for every tenant. Nothing in the API says no. This plan adds a per-key token-bucket limiter as Express middleware, ships it in log-only mode for two days to calibrate, then enforces with a 429 and Retry-After. No new services; the limiter lives in-process and the limits live in the existing config table.

Decision needed

Approve the in-process limiter over a Redis-backed one. In-process means limits are per instance (3× the nominal number across our three replicas), which is acceptable for the abuse case we actually have. Redis is the upgrade path if we ever need exact global limits.

02Context

The public API is a single Express app behind the load balancer, three replicas, sticky sessions off. Authentication resolves an API key to a tenant in authenticate() and attaches it to req.tenant. From there every route is unmetered. The incident on Sep 18 was 41k requests in four minutes from one key, all retries of a failing POST /orders.

What I found

  • Auth middleware already resolves key → tenant before routing, so there's a clean place to hang a limiter — src/api/middleware/authenticate.ts
  • Per-tenant settings already live in a tenant_config table with a JSON settings column; no migration needed for limits — src/db/schema/tenant_config.ts
  • Request logging emits one structured line per request with tenant_id; enough to calibrate limits from existing logs — src/api/middleware/requestLog.ts
  • No existing 429 handling in the SDK; clients would see it as a generic error today — packages/sdk/src/client.ts
Constraints
No new infrastructure this quarter. Zero-downtime deploy. Must not affect the two partners on legacy keys without notice.
Out of scope
Per-route quotas, billing tiers, the admin UI for editing limits. Limits are edited via the existing config CLI.

03Approach

A token bucket per API key, held in process memory, refilled on a timer. It sits directly after authenticate() so it has the tenant but runs before any handler or database work. When the bucket is empty it answers 429 with a Retry-After header instead of forwarding. A per-tenant override in tenant_config.settings.rateLimit beats the global default. A RATE_LIMIT_MODE=log flag makes it observe-only so we can size the limits on real traffic before anything is blocked.

05Risks & open questions

RiskLikelihoodImpactMitigation
A legitimate burst gets throttledMediumMedium48h log-only calibration; per-tenant overrides; default set at 2× the highest observed legitimate rate.
Per-replica limits are too loose to stop the abuseLowMediumSet the nominal limit at ⅓ of the intended global limit. If still insufficient, the Redis option is a drop-in behind the same interface.
Memory growth from many distinct keysLowLowFive-minute prune of idle buckets; we have ~400 active keys, ~100 bytes each.

Open questions

  • Is 60 req/min the right global default, or should it be derived from the calibration query?
  • Should POST /orders get a stricter limit than reads, or is one number per key enough for now?
  • Do we need a migration for tenant limits? No — tenant_config.settings is JSON.
